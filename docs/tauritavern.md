# TauriTavern 适配 tt.8

## 基线

- 千千结：`atonal519/ST-MyriadKnots`，`9447825efd2427b2027a9c26d139c3e7f373fb80`，0.5.4。
- 白鳥 API 参考：`atonal519/ST-BaiNiaoData`，`e86262c`，2026-09-22 新增永久删除接口。
- TT：正式标签 `v2.2.0`，`2b4de4b8a8aab467d9e75d546be84754918cc026`。
- TT 官方接口：[extension.store](https://github.com/Darkatse/TauriTavern/blob/v2.2.0/docs/API/Extension.md)。

## 实现

`src/backend-client.js` 在识别 TT 宿主时选择 `src/tauri-backend.js`；普通 ST/Luker 和调用方明确注入的 fetch 保留原行为。没有全局替换 fetch，模型 API、聊天和世界书请求仍走宿主原有通道。

等待 TT ready 后调用公开的 `tryGetJson / setJson / deleteJson / listKeys / listTables`，这些接口均存在于 TT v2.2.0。不存在的记录返回 404，revision 不匹配返回 409；读盘失败和损坏数据会明确失败，不能当成空记录覆盖。

数据位置：`data_root/_tauritavern/extension-store/qqj-bainiao-v1/kv/`。table 是 namespace 与 collection 的 SHA-256，key 是 recordId 的 SHA-256，原始键保存在文件内容中并在读取时校验。中文、较长键和特殊字符不会直接作为路径使用。

每个键对应一个文件，文件内同时保存当前 envelope 与删除历史。删除、恢复和更新都只提交一次 TT `setJson`，复用 TT 的临时文件替换机制。支持读、写、列出、删除、回收站查询和恢复；回收站没有自动清理。其磁盘布局不同于原白鳥服务端，不能直接互相覆盖或迁移。

tt.2 增加 `DELETE /records/:namespace/:collection/:recordId/permanent`，供新版存储管理及已停止时间事项清理使用。校验 revision 后仅永久删除当前记录，不产生回收站副本；若该键已有旧回收站记录则原子保存这些历史，否则调用 `deleteJson` 释放整个键文件。与新版白鳥一致，此接口不清理旧回收站。普通删除与恢复语义不变。

tt.3 不修改 namespace 或哈希键，不移动现有记忆。写入时将原 `qqj-tt-record-v1` slot 的完整 JSON 字符串放入 `{ format: 'qqj-tt-json-v2', serialized }`，避免原生层重排嵌套对象字段。读取同时兼容旧对象与新封装；下次正常写入才保存为新格式。新格式需要 tt.3 或更高适配，旧适配无法直接读取。

旧版原生存储可能已经重排索引 refs 字段，导致 `V3_GRAPH_INDEX_ROUTE_INVALID`，首次建档只留下 staged 记录却无法提交 root。tt.3 读取旧索引时仅尝试恢复原版明确的字段顺序，而且必须与原有 contentFingerprint 完全吻合；不修改值、数组顺序、ID 或指纹，不删除旧记录。损坏或无法验证的索引仍交给原版校验拒绝。

保留上游列表读取的独立 120 秒超时。升级前请导出 TT 完整数据备份，更新后重启；不需要卸载或完全重构。此前补齐失败的聊天先“刷新状态”，再“补齐缺失”；旧摘要不会自动重跑，旧楼千事需按需补齐。

同一应用运行环境共享写入队列；如宿主提供 Web Locks 则同时使用。TT 的公开 API 没有原生 compare-and-swap，**不承诺多个应用进程、外部文件写入者、设备同步并发写入时的版本原子性**。这是单个 TT 应用内的适配。

取消/超时会阻止尚未提交的写入；已经交给原生层的写入无法撤回，可能在调用方超时后完成。发生此类异常应重新读取确认，不能盲目重试旧 revision。队列会等原生写入结束后才释放。

## tt.4 请求等待与阶段显示

手动摘要提交成功后，原版仍将提取阶段保留为 `committing` 并等待 CSE 人物分析，楼层因此继续显示“正在处理”。现在转入 `analyzingCse`，已保存摘要显示可用，并明确提示“摘要已保存，正在分析人物状态”；仍保留工作锁，避免与未完成的人物分析冲突。CSE 成功或失败后正常释放任务，失败不删除已保存摘要。

模型请求在 fetch、响应正文和 SSE 读取阶段均独立监听超时与取消，宿主实现即使不响应 AbortSignal，也会结束插件侧等待，不采用迟到结果。流式收到 `[DONE]` 即结束读取，不再依赖服务端关闭连接。共享 API 客户端的这部分修复也适用于普通 ST；不改变 API 配置、请求内容或重试规则。

非流式请求受支持，不要求勾选流式。原版 CSE 最多尝试 3 次，180 秒是单次请求的超时；连续超时可接近 9 分钟，外加其他处理时间。这次修复不承诺所有人物分析在 180 秒内完成，也未证实用户的接口实际发生了不响应取消或 SSE 不关闭连接。

## tt.5 楼层卡片独立显示

「设置 → 通用设置 → 外观」提供「显示楼层召回卡片」与「显示楼层记忆卡片」，默认均开启。两项全局设置分别保存为 `inlineRecallVisible` / `inlineMemoryVisible`；旧配置缺少这两个字段时保持显示。

关闭任一项会移除对应整块楼层卡片，不留占位；重新开启时从现有记忆与回执恢复显示。隐藏的卡片不参与 DOM 挂载重试，切换聊天、加载旧楼和重启后继续遵循选择。仅改变楼内渲染，不修改聊天、记忆或召回任务，也不隐藏主面板中的摘要和诊断。

## tt.6 批量补齐阶段显示

历史补齐的摘要与 CSE 会并行执行，摘要任务结束后，批量任务原先仍向界面报告 `extracting`。现在状态投影依据实际子任务，将没有摘要任务、仍有人物分析的批次报告为 `analyzingCse`，其余收尾阶段报告为 `syncing`。不改变工作锁、调度顺序或已保存内容。

摘要页分别显示已保存楼数与后续人物分析／同步阶段；任务完成后的订阅通知也会更新打开面板时生成的通用“正在处理”提示，保留具体操作反馈与错误提示。tt.4 的单楼修复和 tt.5 的独立外观开关继续保留。

## tt.7 同步原版 0.5.2

同步千事历史补齐的逐楼结果、重复候选人工审阅、已审结果本地结案及聚合摘要召回等修复。人工确认窗口沿用原版流程；打开或取消计划不调用模型、不写入结果。升级本身不自动补齐旧千事记录，不需要完全重构。

保留 TT 原生存储与旧索引兼容、manifest 作者字段、请求超时与取消处理、两个独立楼层卡片开关，以及单楼／批量任务的状态显示修复。此版本没有改变 CSE 模型请求与重试策略，不承诺人物分析提速。

同步验证中发现原有提前固定测试依赖短延迟，偶尔漏掉正文编辑、删除或 swipe 后的迟到 token。现在这些事件会同步撤销尚未触发的提前固定许可，已启动任务仍沿用依赖检查。测试直接检查地基调用，确认迟到 token 不再触发旧许可。

## tt.8 同步原版 0.5.4

包含 0.5.3 的千事归档简化：可用事项直接归档并参与召回，取消 tt.7 所对应的人工审核结案流程；旧待审候选仍可只读参与图与召回，不自动覆盖正式事件或改写旧楼。同步日期计算调整，不对不确定的跨月、跨年关系作猜测。

正式千事事件右侧三点菜单增加“编辑详情”，可修改标题和经过说明，保留事件身份、时间和关系；旧审核候选仍只读。升级不自动重做旧摘要。TT 存储、两个独立显示开关、阶段提示和迟到 token 取消修复均保留，CSE 请求与重试策略没有调整。

## 本地开发

```sh
npm ci
npm run build
node scripts/tt-stamp.mjs
npm test
```

上游 `tests/settings-api.test.mjs` 要求本仓库同级目录有 `ST-SevenDaysCal/runtime/settings.js`（来自 atonal519/ST-SevenDaysCal），仅为测试夹具，不是使用本适配版的必装依赖。

本分叉的前端业务版本为 0.5.4，适配版本记为 tt.8。更新上游后需要重新构建、生成缓存哈希并回归验证；不要直接用原版 dist 覆盖本分叉。
